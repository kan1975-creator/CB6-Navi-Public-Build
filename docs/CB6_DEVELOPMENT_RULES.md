# CB6 Navi 開発運用ルール — 統合正本

更新日：2026-11-18
適用範囲：CB6 Navi の会話応答、調査、実装、GitHub登録、Actions、APK、実機確認。
**位置づけ：運用ルールの単一参照文書。** 機能仕様、過去Runの実績、ACTIVE Registry自体を置き換えない。既存ACTIVE Registry・Coverage・Freeze・Verifier・Workflowは変更しない。本書のGitHub登録だけで機械的強制・ACTIVE化・将来の全チャット自動遵守が成立するとは主張しない。

## 1. 優先原則と工程管理
1. 動作するAPKの完成を最優先とし、必要な安全性・整合性条件は守る。工程番号増加を進捗とみなさず、無意味な工程分割、調査反復、ガバナンス工程を増やさない。
2. 目的・具体的成果・完成条件を先に定義し、実行できる関連作業を可能な範囲で一括する。
3. 既存PASS・既存証拠・承認・STOPを継承する。変更により根拠が失効した範囲以外を再試験しない。未検証をPASSに格上げしない。
4. ユーザー未指定の前提条件（例：技術的必要性が未証明の完成ZIP）を追加しない。
5. 重大な不具合の既知履歴を設計前に確認し、推測修正・対象外変更をしない。

## 2. 過去記録・既存資材の確認と再利用
1. 回答開始時、STOP判断前、次工程・Work・別GPT・添付／再添付指示前に、現在会話、利用可能な過去チャット・Work記録、既存ZIP・ログ・成果物、PASS／FAIL／STOP、同一調査結果を確認する。
2. 確認範囲・差分・新たに得られる証拠・実行可能な手段・Work利用の必要性を区別する。全履歴を取得していない場合は「全文確認済み」と言わない。
3. アクセス可能な同一資料の再添付を求めない。アクセス不能は「未確認」であり「不存在」ではない。
4. 再添付が不可避なら、ファイル名、必要な部分、目的、既存証拠で代替できない理由、最小の添付・送信手順を示す。
5. Work利用枠を浪費せず、既存成果を優先再利用する。ユーザーがWork不使用を指定した場合は従う。

## 3. 表示・報告ルール
1. 開発の進捗回答は冒頭に詳細工程番号を示す。ただし新しい作業実体のない工程番号を量産しない。
2. 既存PASS／今回確認／FAIL／未確認／STOPを区別する。実施した操作と未実施の操作を明記し、証拠のない「完了」「成功」を禁止する。
3. 結論、根拠、残件、次の安全な行動を簡潔に示す。STOPなら理由と未解除の制限を明記する。
4. 実績は取得可能なコマンド・終了コード・SHA・変更パス・Commit・Run・Artifactの証拠に基づく。
5. 「ソース確認」「コンパイル成功」「APKビルド成功」「インストール」「実機動作確認」を混同しない。診断ArtifactをAPKと呼ばない。
6. ACTIVEの進捗報告契約（非待機4行／待機6項目など）を勝手に変更しない。ボタン・説明・証拠の追加との整合は未確認として扱う。

## 4. ボタンルール（必須）
1. **安全で実行可能な開発進行手段が一つでもあれば、用途に合う実際に機能する操作ボタンを表示する。** STOP中も同じ。開発を断念したという理由だけで省略しない。
2. このチャットで通常継続する場合は「進める」（旧記録の「進めて」表記も原文として保持）。押すと**この会話に指示が送られる**。外部操作の成功を意味しない。
3. 新たな本人承認が必要な場合のみ「承認して進める」。対象、許可範囲、禁止事項を明記する。押下は承認指示の送信であり、GitHub・Actions・ビルドの実行保証ではない。
4. 「コピー」は別チャット・Work等へ引き継ぐ必要がある場合に限る。コピー対象と、コピー→指定先へ貼付→内容確認→送信→結果確認の手順を明示する。コピーだけでは実行・承認されない。
5. ボタンごとに「押すと何が起こるか」「押した後の本人の操作」「結果確認」「その後の行動」「実行されないこと」を短く説明する。実際に外部操作できないボタンを作らない。
6. 安全な進行手段が**一切ない場合に限り**省略できる。その際は確認済み証拠、検討した代替手段、具体的な進行不能理由、未確認事項を記載する。単に「操作する作業がない」だけでは省略できない。
7. 旧工程425-R-20の広い省略条件は、後発K節で撤回済み。B・B追加・I・J・K間の全面的優先関係は原本上未確定であり、独断で規則を置換しない。
8. 過去の工程425-R-7の「ボタン欠落」「操作説明欠落」FAIL2件は未解決履歴として保持する。文書登録だけで是正完了としない。

## 5. STOP・承認・変更権限
1. STOPは根拠ある具体的原因で判定し、実施済み／未実施／未確認／解除条件を示す。同一原因でSTOPを反復せず、次は実行可能な別経路、最小入力、または不可能な理由を示す。
2. STOPをボタンや別チャット指示で迂回しない。安全な読み取り・記録等が可能なら提示する。
3. 本人が最終決定権を持つ。承認は特定の変更・対象・範囲に限定し、別変更へ流用しない。承認前の修正、事後承認、無承認のGitHub書込・Actions・APKビルド・SQLite更新・Release・正式採用・STOP解除を行わない。
4. 実装不具合修正の承認記録・独立レビュー・変更範囲限定試験・必要箇所の実機受入は、適用される既存ACTIVE契約に従う。個人利用の簡略化提案をACTIVE変更済みと扱わない。
5. GitHub書込時は対象ブランチ・HEAD・競合・対象外変更を確認し、非強制更新する。Actionsは承認済みの新規Run回数を守り、旧Runの再実行を無断で行わない。
6. 書込が自動Actionsを誘発し得る場合は事前にトリガーを確認する。「Actionsを起動しない」指示と衝突する場合は書込前にSTOPし、別の安全な方法を選ぶ。

## 6. 実装前の品質・性能確認
1. 過去の地図フリーズ、表示欠落、重複描画を確認し、変更箇所のJava／JNI／C++／描画／ライフサイクル／リソースを追う。
2. UIスレッドの負荷を確認する。デバウンスや450ms待機は重い同期処理の解決策ではない。
3. オフラインMWMを別スレッドで扱う前にネイティブのスレッド安全性を確認する。キャッシュ、取得範囲、古い結果の破棄、画面移動・縮尺変更・復帰を設計する。
4. コンビニのオフラインMWM、既存UserMark、6ブランド画像と承認済みサイズ、信号機E1005は明示的な変更要求がない限り保護する。
5. 地図スクロール・ズームの応答性を完成条件に含める。固定半径3kmを最適と決めつけず、実機で必要な範囲のみ確認する。
6. ビルド前に変更差分を静的に確認し、失敗時は最初の具体的エラーを基に最小修正する。不要な既存PASS再試験は禁止。

## 7. 回答ごとの必須点検
- 過去記録照合：確認済み／一部確認／未確認（範囲・理由）
- 重複排除・一括化：適合／要是正
- 実行可能性・Work節約：適合／未確認／要是正
- 表示・ボタン・STOP条件：適合／要是正
- 送信前6点：①工程番号 ②必要な実効ボタン ③押下動作 ④本人の次操作 ⑤非実行事項 ⑥過去記録確認範囲
- これらは**回答ごとに実施**する。文書への登録を遵守PASSの代わりにしない。
